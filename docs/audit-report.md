# DriftGuard hardening audit

Initial audit completed on 2026-10-15 (Asia/Calcutta), before implementation changes. This report is based on repository source at `be5f034`, not on the separately supplied four-run presentation summary.

## Scope and method

The audit covered the README and project documentation, frozen contracts, mock provider and mutation manager, orchestrator API and execution paths, failure observation/classification, deterministic planner and validator, LLM boundary, restricted patch transformations, candidate staging and commit, retry and verification controls, registry locking/versioning, SQLite audit and metrics, baseline agent, evaluation runner, frontend, tests, environment configuration, and build/deployment assets.

Severity definitions:

- **Critical** — can cause unsafe execution, false commit, retry loop, or an incorrect benchmark.
- **High** — can break the core demo or invalidate a metric.
- **Medium** — weakens explainability, reproducibility, or usability.
- **Low** — polish, documentation, or presentation issue.

| Failed verification | Candidate is discarded in `finally`; active registry remains unchanged. | Mock/evaluator has no deterministic verification-mismatch scenario, so this invariant is not benchmarked. | High | Add evaluator-controlled mismatch behavior and assert no commit/version change. | `orchestrator/healing/recovery.py`; `tests/healing/test_recovery.py` |
| Atomicity/versioning | Per-tool re-entrant lock, base-version checks, immutable snapshots, and atomic whole-definition activation prevent stale overwrite in-process. | Registry is memory-only; process restart loses verified repairs. The benchmark lacks a stale-version raw trial. | High | Benchmark concurrent stale candidates; state the in-memory durability limitation. Do not claim restart persistence. | `orchestrator/registry/service.py`; `docs/INTEGRATION.md` |
| Safe-stop outcome | Recovery has granular failure statuses, but agent/API runs generally terminate as `failed` with string reasons. | No authoritative top-level machine-readable `safe_stop` outcome/category; evaluator infers refusal from failed status and no side effect. | Critical | Add explicit `safe_stop`, reason code, error category, and terminal outcome semantics across agent, API, audit, and benchmark. | `orchestrator/healing/recovery.py`; `orchestrator/agents/healing.py`; `evaluation/runner.py` |

## Initial implementation priority

1. Introduce an authoritative typed safe-stop result and complete deterministic scenario matrix for the fixed notification task.
2. Add independent notification-state verification, one-retry enforcement evidence, and atomic schema/adapter commit assertions.
3. Replace the current narrow runner output with reproducible raw artifacts and correct metric formulas, including cold/warm reuse and fair baseline comparisons.
4. Add tests for the missing scenario, artifact, and metric invariants.
5. Wire the compact summary into the frontend, correct stale documentation, and add Docker/build validation.

The audit intentionally makes no claim that the repository currently satisfies the requested benchmark or that the supplied four-run results are reproducible from this checkout.
